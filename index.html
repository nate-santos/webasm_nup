webasm_nup

Folder, zip, or 7z → .nup, entirely in your browser

WASM: loading…No uploadsNUP v1

Pack an unencrypted NX game dump into the .nup container format (spec: a55uka/nup). Hashing and zstd compression run in WebAssembly, files are streamed in 1 MiB chunks, and the result is written to browser storage (OPFS) — so a multi-gigabyte game never has to sit whole in RAM.

Your files never leave this device. Nothing is uploaded, and no keys or decryption are involved: .nup holds unencrypted dumps only.

1 · Input folders, zips, or 7z files

Add a dump bundle (base/ + updates/ + dlc/), a bare content folder (exefs/ / romfs/), or several folders that together make up a game — or a .zip / .7z containing any of those layouts. Each input is scanned locally and its packages are listed below. Archives are streamed, not loaded whole: zips support Stored and Deflate (plus zip64); 7z supports Copy, LZMA, LZMA2, Delta, and x86 BCJ (the usual 7-Zip/py7zr chains, solid or not). Encrypted archives and other methods (BCJ2, PPMd, BZip2, other BCJ variants, AES) are rejected with a clear error. If you create the archive yourself, prefer Stored — a compressed archive is decompressed and then re-compressed with zstd, which is wasted work. 7z files fetch a small extra decoder (lzma.wasm, ~17 KB) on first use.

3 · Convert

Output is written to browser storage first (OPFS, file game.nup), then you save it where you want — unless you pick direct save, or the input is over 2 GiB (auto mode), in which case it writes straight to a file you pick and skips the OPFS copy. Large files (> 256 MiB) are stored raw, like Eglantine's writer; smaller files are zstd at the level chosen below, falling back to raw when compression doesn't shrink them. Before converting, the site checks browser storage quota and requests persistent storage; if OPFS can't hold the worst-case output, it writes directly to a file you pick instead, rather than failing halfway.

How it works

  • WASM core: nup.wasm (C + upstream zstd 1.5.7, built in wasm-src/) does streaming SHA-256 and streaming zstd. JS only orchestrates files and writes the superblock / TOC / meta TLVs.
  • Storage, not RAM: input is read in 1 MiB chunks and output goes to OPFS (or straight to a picked file on large runs). The only whole-file reads are the tiny main.npdm / main header used to find the title ID and build ID.
  • Compatible layout: superblock, TOC, 16-byte-aligned extents, dedup by (size, SHA-256), .listing files excluded, update-only dumps flagged standalone_update — verified against the reference Python nup verify tool in test/.
  • Browser support: folder picking works best in Chrome / Edge (showDirectoryPicker). Other browsers can use the file-picker fallback. OPFS is required for the storage-backed output; if it is unavailable, the site falls back to writing straight to a file you pick with the save dialog.
